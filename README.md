## 设计目标
开放式虚拟修仙文字游戏。玩家用脑洞打字当输入；**对局输出只抽已入库事件**。没有主线，剧情全随机。大模型不参与对局接龙，只用于**把新事件写进事件库**。

**核心玩法**：
`玩家发送文字命令 → 先改人物状态（地点/时间/基础行动） → 再按新状态触发事件 → 事件再改人物状态`

核心述求（能力）：
1.  虚拟地图/世界地图/城市地点的生成与编辑。
2.  事件录入系统：支持人物、地点（可为类型如“酒馆/酒楼”）、时间、持续时间、结果（秘籍、宝物、丹药正/负面、事件等）。场景可用前端流程图定制（仅单条事件内部）。可用大模型按同一结构**生成草稿并写入事件库**（须校验后发布）；对局中不现场生成。
3.  虚拟人物录入，按人物特征随机匹配事件，人物有出生时间（例：太乙历一百年、某城、六岁孩童）。
4.  事件触发概率生成器：命令落地后，按**当前状态**从合格池加权随机（向量可辅助）；无“下一章”。
5.  吃饭、打坐、突破、围观、买鱼、拜师等与奇遇同一套事件模型，一律由聊天命令或事件连锁触发。
6.  全局万年历生成器（有界面），可设置游戏时间与现实时间的比例。

**输入 / 输出**：输入只有玩家脑洞文本。对局输出 = 事件库抽中的叙述 + 结构化状态差分。大模型只出现在录入侧：描述想法 → 填表草稿 → 校验 → 发布入库，之后对局才能抽到。

# EventHorizon 修仙版 - 架构与游戏设计文档
## 第一部分：底座设计
### 1.1 概述
基于 EventHorizon v2.0 的通用事件驱动底座，针对“文字修仙游戏”的特定需求（高自由度、长周期、复杂因果、叙事多样性），本节对底座在时空管理、叙事逻辑、智能检索和模拟推演四个维度进行核心扩展。

**产品边界**：单机、单存档、单主角。开放式文字沙盒：操作入口是**聊天框**，不是技能栏或任务面板。类型为文字修仙；物资消耗只做到生存层，不做工坊经营。文中“全局”指当前存档世界。

**无主线**：不实现任务日志、章节、必经 BOSS、既定结局。引擎不调度“故事进度”。玩家想成仙、复仇或活下去，只能通过聊天触发事件、改状态去碰，事件可被错过、可永不发生。

**玩法核心**：两段状态变化。第一段由玩家命令落地；第二段只从事件库随机抽（抽空则酒楼无事）。聊天原文不直接改数值。

**分期交付**：
*   **MVP**：手填地图、万年历、事件库接龙、聊天命令、单主角、存档、新鲜感基础（记忆衰减/文案变体）。**对局关闭大模型**。录入编辑器可用 `LlmEventAuthor` 生成事件草稿并入库。
*   **V1**：流程图 JSON + 聊天选分支；日程与关系网；`EventArbiter`；`CauseLink`；标签配额与长尾保护。
*   **V2**：向量匹配、可选对局临时生成（`LlmEventWriter`）、地图编辑器、转世/夺舍。
### 1.2 时空服务扩展
#### 1.2.1 万年历模型
**设计目标**：支持长时间跨度的游戏进程，提供具有文化特征的时间感，并作为触发周期性事件的基础。
*   **时间结构**：定义 `GameCalendar` 实体，层级为：`纪元 -> 年(干支) -> 月 -> 日 -> 时辰`。
*   **流速控制**：在 `GameEngine` 中增加 `TimeDilation` 配置项，支持动态调整游戏时间与现实时间的比例（如 1:1，1:60，1:86400）。
*   **事件驱动**：日历服务内部维护循环，定期发布 `TimePassEvent`（如`时辰更替`、`日出日落`、`月圆之夜`）。特殊日期（如每甲子一次的“灵气潮汐”）会发布特殊的 `CosmicEvent`。
#### 1.2.2 虚拟地图模型
**设计目标**：支持从宏观世界到微观地点的动态生成与管理。
*   **图结构定义**：采用图结构存储地图。`Location` 节点包含坐标、类型（城市、荒野、洞府）、属性（灵气浓度、危险等级）。`Route` 边定义节点间的连通性及移动消耗。
*   **生成原则**：世界层手编（一份可编辑的世界地图）；城市内节点按模板生成（集市、山门、遗迹）；建筑内部按需加载嵌套子图。预留 `MapGenerator` 接口，MVP 不实现柏林噪声地貌或自动铺路。
*   **动态性**：地图节点挂载事件监听器。当节点状态发生剧变（如大战发生），触发 `MapUpdateEvent`，可动态修改地图拓扑或属性（如森林变为焦土）。
### 1.3 叙事引擎扩展
#### 1.3.1 可视化流程图数据结构
**设计目标**：支持通过前端界面定制**单条事件内部**的分支，底座负责解析和执行。不用于编排全局主线。
*   **剧情图模型**：定义 `ScenarioGraph`。
    *   **节点**：包含类型（对话、旁白、战斗、获得物品）、内容文本、参数（如战斗ID）。
    *   **边**：定义从节点 A 到节点 B 的跳转条件。条件只允许谓词白名单组合（`AND` / `OR`），执行器不做字符串 `eval`。谓词示例：`attr_gte(境界, 筑基)`、`has_item(玉佩)`、`flag(已拜师)`、`location_type(酒馆)`、`has_cause(仇恨, 玩家)`。
*   **执行引擎**：增加 `ScenarioExecutor` 组件。它维护一个“剧情上下文栈”，根据当前玩家/角色的状态，计算边的谓词真值，决定**本条事件内部**走向。流程图禁止引用“主线步骤/章节 id”。MVP 用 JSON 描述图；可视化编辑器放到 V1。
#### 1.3.2 事件库与录入系统
**设计目标**：实现海量事件的标准化录入与分类管理。吃饭、打坐、突破、奇遇、归宿等**同一套 `GameEvent` 模型**，差异只在元数据、谓词和结果，不另开指令类型。
*   **事件元数据**：适用地点（或地点类型）、适用时间、前置谓词、触发权重、冷却、同一 Agent 最大触发次数、互斥标签、默认优先级（供仲裁）、可选标签（如 `生活` / `修炼` / `突破` / `奇遇`）。
*   **触发来源 `TriggerSource`**：`player`（聊天解析命中）、`schedule`（日程提高某标签权重后随机）、`encounter`（粗筛后加权随机）、`force`（天劫、死亡等系统写入）、`chain`（其它事件结果池连带）。来源不是事件类型，只是本次投递的字段。
*   **聊天别名**：每条事件可配触发短语（如 `eat` ← “吃饭”“去吃点东西”“果腹”），供 `ChatParser` 使用。
*   **结果池配置**：物品掉落或消耗（正/负面）、状态变更（饱食、修为、中毒、顿悟）、检定（突破成功率等，读 `BalanceTable`）、写入 `CauseLink`、触发连锁事件、可选绑定 `ScenarioGraph`。
*   **生活事件示例（与奇遇同一录入界面）**：
    *   `eat`（吃饭）：谓词可要求有食物或允许饥饿分支；结果扣食物、加饱食；无食物则结果池走饥饿分支并可能 `chain` 求食事件。
    *   `meditate`（打坐）：耗时、按灵气加修为；可带闭关标记以启用局部加速结算。
    *   `breakthrough`（突破）：谓词 `修为满值`；结果做突破检定；极端失败 `chain` 走火入魔（`force`）。

#### 1.3.3 事件录入编辑器交互
**设计目标**：让非程序人员能安全产出合规的 `GameEvent`，编辑器只允许拼装白名单谓词与结果类型，不暴露自由代码，保证产出的 JSON 能被 `EventRegistry` 正确反序列化。

*   **信息架构**：三层——事件列表（筛选/搜索/标签/状态）→ 单事件详情表单（元数据 + 结果池）→ 内嵌流程图画布（仅当挂了 `ScenarioGraph` 时展开）。三层共用同一份未保存草稿，离开时确认。
*   **元数据表单**：地点/地点类型（下拉+多选，支持"任意"通配）、时间窗口（时辰多选或"任意"）、前置谓词构建器、触发权重（数值+当前所在合格池的相对占比预览）、冷却、最大触发次数、互斥标签、默认优先级、标签（生活/修炼/奇遇…复选）、聊天别名（标签输入框）、`NoveltyWeight` 曲线覆盖（可选，默认继承全局曲线）。
*   **谓词构建器**：不写表达式，选"谓词类型"（`attr_gte`/`has_item`/`flag`/`location_type`/`has_cause`…）+ 参数下拉/输入，多条用 `AND`/`OR` 分组框拖拽组合；保存时后端仍按白名单校验，编辑器只是前端约束，不是唯一防线。
*   **结果池编辑器**：按结果类型（物品掉落/消耗、状态变更、检定、写 `CauseLink`、连锁事件、绑定流程图）分 Tab，各自独立小表单；连锁事件字段引用已存在的 `eventId`（下拉搜索，防止手填打错字导致读档丢事件）。
*   **文案变体面板**：`EventVariant` 列表，支持占位符（如 `{地点}`/`{境界}`）预览，至少要求 1 条默认文案。
*   **流程图画布**：复用 1.3.1 的节点/边模型；节点面板拖拽创建，边的条件复用同一套谓词构建器；画布内禁止跨事件引用（不能连到别的 `eventId` 的节点），从数据结构上保证"仅单条事件内部"。
*   **联动校验**（保存前阻断）：物品 ID / eventId 引用是否存在、谓词参数类型是否匹配、流程图是否有孤立节点或环、互斥标签是否与自身冲突。校验规则与运行时（`EventRegistry`/责任链校验节点）复用同一套定义，避免编辑器与运行时"两套标准"。
*   **测试沙盒**：录入页内置"模拟触发"——输入一份测试用 `{地点, 时间, 境界, 金钱…}` 快照，跑一遍粗筛+谓词，显示是否进入合格池、相对其它候选的权重占比、随机抽样 N 次的命中分布；不用启动完整游戏客户端就能验收一条事件。
*   **草稿/发布状态**：事件可存为草稿，草稿不进入 1.4.2 粗筛的合格池，避免调试中的半成品事件污染正式游玩；发布后写入 `schemaVersion`，与 3.4 工厂模式的版本兼容策略衔接。
*   **批量与复用**：支持"复制为新事件"，导入/导出 JSON。可用 `LlmEventAuthor` 一次生成多条草稿（见 1.3.4）。

#### 1.3.4 大模型辅助入库
**设计目标**：用大模型**扩事件库**，不对局现场编故事。产出必须能被 1.3.3 同一套校验收下。

*   **入口**：录入编辑器内「用描述生成事件」。输入自然语言（例：「酒楼里有人钓到金龙鱼，围观后可买；有钱则鱼或为龙，给报酬」）+ 可选约束（地点类型=酒楼、年龄下限、标签=奇遇）。
*   **产出**：一条或多条 `GameEvent` JSON：元数据、谓词白名单、结果池、聊天别名、`EventVariant` 文案；可选 `ScenarioGraph`（仍禁止章节 id）。
*   **校验**：与手工保存相同——物品/eventId 须已存在或标为「待补物品」草稿；谓词类型白名单；金钱/境界只许走结果类型。失败则标错误字段，不入库。
*   **状态**：默认 **草稿**，不进合格池。人工点发布（或校验全绿后一键发布）才参与对局抽取。
*   **去重**：生成后与库内标题/向量（若已有 embedding）比对，相似度过高则提示合并或只加变体，避免同一金龙鱼刷十几条规则重复的事件。
*   **对局隔离**：`ChatParser` / 第二段抽取 **不调用** `LlmEventAuthor`。库空只输出「无事发生」，不会在玩的时候问模型要剧情。

### 1.4 向量事件系统扩展
#### 1.4.1 向量存储与检索服务
**设计目标**：用语义相似度补规则触发的盲区，而不是替代规则。MVP 可关闭本模块，事件只走元数据过滤 + 权重随机。
*   **基础设施**：优先 SQLite 存事件元数据；向量索引 V2 再接入（轻量库或内存索引）。事件 embedding 在录入时预计算并缓存，不在触发时现场编码全库。
*   **嵌入接口**：定义 `EmbeddingService`，负责将事件描述、`CauseLink` 摘要转为向量。状态上下文优先读结构化字段和因果标签，避免每次把整段中文状态拼进去再 embedding。
#### 1.4.2 两阶段匹配
**设计目标**：命令落地后，按新状态**只从事件库**抽一条；抽空则第二段无事。没有故事导演。MVP 不对局调用大模型。
*   **粗筛（规则，走索引）**：命令造成的地点/时间/年龄/境界、前置谓词、冷却、次数、互斥。结果集即本轮合格池（例：地点类型=酒楼 → 酒楼事件）。
*   **重排与随机**：合格池加权随机。命令本身不指定“接下来必须金龙鱼”。
*   **门控**：未过门控则第二段可以“酒楼无事”，只保留第一段命令的状态变化。
*   **上下文**：`{历法年, 出生地, 年龄, 地点, 天气, 境界, 金钱, CauseLink[]}` 以及刚落地的命令摘要。
*   **禁止项**：全局 `questId`、章节解锁、强制下一事件队列（`force` / `chain` 除外，chain 只做结果池有限连带）。

#### 1.4.3 新鲜感与去重机制
**设计目标**：长周期游玩下，避免同一地点/标签的事件反复命中，让"随机接龙"变成"循环播放"。机制只加在重排阶段的权重计算上，不新增总线事件、不改仲裁与状态机。

*   **短期记忆衰减**：新增 `AgentEventHistory`，记录该 Agent 最近 N 次触发的 `eventId` 与触发游戏时刻。重排时对合格池中每条候选乘以 `NoveltyWeight`：距上次触发越近权重越低，随时间/次数推移恢复到 1；比现有"冷却"更细腻——冷却是 0/1 开关，冷却一过立刻满权重容易撞车，这里是渐进恢复。
*   **标签配额**：`AgentEventHistory` 同时按标签（生活/修炼/奇遇…）滚动计数。某标签近期占比偏低时给该标签下的候选一个补偿乘子，避免高权重标签长期压制其它标签；是软性配额，仍在同一次加权随机里生效，不是硬性排期。
*   **长尾保护**：`triggerCount == 0` 的事件给一次性权重加成，避免权重配置不当导致某些事件永远抽不到；一旦触发过就回到常规曲线。
*   **文案变体**：`GameEvent` 结果确定时允许挂多条 `EventVariant`（叙述文本），命中同一 eventId 时优先选未用过或最久未用的变体。成本最低，不涉及规则/结果改动，MVP 即可做。
*   **V2：向量新颖度**：并入已规划的 `VectorEventGenerator` 重排步骤——用 `EmbeddingService` 比较候选事件与该 Agent 最近 K 条事件摘要的相似度，相似度高则再打一次折。与规则新颖度是同一步的两个乘子，不是两套系统。
*   **落地位置**：全部乘子只作用于 1.4.2"重排与随机"这一步；产出后仍走原门控与 `TriggerSource` 分级，不影响 `EventArbiter` 的抢占/入队/丢弃判断。

### 1.5 智能体生命周期扩展
#### 1.5.1 NPC 履历模拟
**设计目标**：让 NPC 在遇见玩家前就拥有“人生”，增加世界的真实感。
*   **离线模拟**：仅对同城、带未过期 `CauseLink`、或玩家查询过的 NPC 展开细履历；其余用模板一句生成。细模拟同样从事件库随机抽关键事件（步数上限例如 8），不是写死生平剧本。
*   **履历存储**：模拟生成的关键事件写入 `Biography` 事件流，供玩家查询或作为对话素材。
#### 1.5.2 日程：触发一般事件
**设计目标**：NPC（及主角可选）在特定时辰自动从事件库里触发生活事件，而不是发布专用 `IntentEvent`。
*   **日程表**：`Schedule` 把某时辰的权重偏向某一标签（如午时提高 `eat` 权重），**不保证**该时辰必触发该事件。
*   **触发**：空闲且时辰命中时，将该标签并入本轮合格池再加权随机，以 `TriggerSource=schedule` 发布抽中的那条；抽不中则本轮无事。与玩家侧同一条总线。
### 1.6 时间模型统一设计
**设计目标**：调和“全局流速控制”与“个体时间留存”两个看似冲突的需求，保证所有模块对“当前时间”的理解一致。

采用 **全局主时钟 + 个体时间偏移** 模型，而非每个 Agent 独立时钟：

*   **全局主时钟 `GameClock`**：唯一权威时间源，按 `TimeDilation` 推进，发布 `TimePassEvent`。所有周期性事件（灵气潮汐、天劫推算）绑定主时钟。默认墙钟流速保持稳定；**闭关不改全局流速**。
*   **个体时间锚 `AgentTimeAnchor`**：每个 Agent 维护一个 `lastSyncedGameTime`（上次结算的游戏时刻）和 `pendingDuration`（正在处理的事件占用时长）。Agent 的“当前游戏时间” = `lastSyncedGameTime + pendingDuration`。
*   **闭关 = 局部加速结算**：闭关只推进该主角的 `pendingDuration`（如界面 1 秒结算 1 游戏日），同时按结算跨度消耗寿元。世界内其他 NPC 仍按主时钟走动；玩家出关时用时间差决定错过了哪些全局事件（灵气潮汐等），而不是把全世界一起快进一百年。
*   **时间留存语义**：玩家离线时主角 `lastSyncedGameTime` 不随墙钟空转，避免剧情被现实时间扯断。上线后从锚点继续，不强制对齐“此刻主时钟上正在发生的每一件事”。
*   **冲突仲裁**：当 Agent 需要与全局事件交互时，以其时间锚与主时钟的偏差决定是否“错过”，而非强行对齐。

### 1.7 事件仲裁机制
**设计目标**：多源事件（时间、地图、聊天指令、日程、奇遇）并发产生时，统一裁决优先级与互斥关系，避免行为冲突。

*   **事件源分级**（读事件元数据的默认优先级，投递时的 `TriggerSource` 可覆盖）：
    1.  **强制级（Force）**：天劫、走火入魔、死亡等 `TriggerSource=force` 的库内事件——立即中断当前行为。
    2.  **玩家级（Player）**：聊天解析命中的一般事件（吃饭、打坐、突破、移动）——抢占日程触发的事件。
    3.  **日程级（Schedule）**：日程提高权重后随机抽中的同一批一般事件——可被聊天指令抢占。
    4.  **奇遇级（Encounter）**：粗筛后加权随机命中的一般事件——仅当 Agent 处于空闲或探索类行动中时挂接；是否接受也通过聊天回复。
*   **仲裁器 `EventArbiter`**：所有事件进入统一队列前先经仲裁器。仲裁器按 Agent 当前状态与事件等级决定：立即执行 / 入队等待 / 丢弃。吃饭与奇遇没有两套管线。
*   **互斥规则**：同一 Agent 同一时刻只能处理一个“主行为事件”；奇遇事件不抢占主行为，而是作为“可选分支”挂在当前行为上，待主行为结束或玩家主动选择时触发。

### 1.8 持久化方案
**设计目标**：支撑长周期游戏进程，保证世界状态、NPC 履历、地图变更可持久化与回滚。

*   **分层存储**：
    *   **全局快照**：定期（如每游戏日）对 `GameClock`、所有 `Location` 节点属性、当前世界环境状态做全量快照。
    *   **增量事件日志**：所有发布过的事件以追加日志形式存储（Event Sourcing），用于回放与审计。
    *   **Agent 状态**：每个 Agent 的属性、`Biography`、`Schedule`、`AgentTimeAnchor` 独立存档，支持单角色存读。
*   **地图变更回滚**：`MapUpdateEvent` 记录变更前后的节点属性 diff，支持按事件 ID 回滚（如“焦土复原”剧情）。
*   **存档结构**：单存档 = 全局快照 + 自上次快照以来的事件日志 + 全部 Agent 状态。读档时先载入快照，再重放增量日志至目标时刻。
*   **NPC 履历存储**：`Biography` 以事件流形式存储（非全量文本），按需懒加载渲染，避免长生平履历占用过大内存。

### 1.9 因果模型
**设计目标**：把“仇杀、拜师、前世因果”收成统一数据，避免关系网、向量检索、流程图各写一套 if。

*   **结构 `CauseLink`**：`Actor`、`Action`、`Target`、`Tag`、`ExpiresAt`（可选）。例：杀李四 → `{玩家, 击杀, 李四亲友, 仇恨, 20年}`。
*   **写入时机**：事件结果池、死亡流程、流程图节点结算时追加；过期后检索不再命中。
*   **读取方**：粗筛谓词（`has_cause`）、关系网（追杀令/守孝）、转世时部分 Tag 可继承。
*   **约束**：只存标签与过期，不存自由文本推理；一条行动可写多条 Link（仇人、目击者、宗门）。

### 1.10 物品与战斗（薄层）
**设计目标**：让吃饭、炼丹、突破、流程图“战斗节点”接得上，不先做经营或动作战斗。

*   **物品**：`Item` 含类型（丹药/秘籍/食物/材料/装备）、堆叠、唯一性、正负面效果。背包按 Agent 存。没有生产链；物资来自事件结果池的掉落或消耗。
*   **战斗**：文字检定，不做成回合动作。`P(胜) = clamp(境界差 + 道具 + 运势 − 心魔, 0.05, 0.95)`。失败可伤势、溃逃或死亡；胜利写入掉落与可选 `CauseLink`。聊天里说“动手”“逃”映射到该事件流程图节点或结果分支。

### 1.11 文字命令（输入）
**设计目标**：玩家唯一输入是脑洞文本。命令先改状态，再打开事件抽取。

*   **解析 `ChatParser`**：一句话 → `{ 地点?, 行动, 对象?, args }`。例：“去酒楼吃饭” → 地点=酒楼，行动=eat；“去围观” → 行动=watch，对象=当前场景焦点（金龙鱼摊）。
*   **第一段（命令落地）**：发布命令型 `GameEvent`（`TriggerSource=player`）。结果池改状态：移动到酒楼、推进时间、扣饭钱、加饱食。谓词不过则第一段失败（没路费到不了酒楼），不抽第二段。
*   **第二段（事件触发）**：用更新后的状态从**事件库**粗筛并随机一条（或抽空）。不在此处调用大模型。
*   **再输入**：玩家对叙述继续脑洞（“把鱼买下来”“求拜入门”），再走同一两段循环。买鱼要过 `has_item/金钱`；六岁求入门可由事件允许或拒绝，由谓词与结果决定，不是主线必过。
*   **流程图**：单条事件内的选择也用下一句聊天，不 `eval`。

### 1.12 对局输出与模型边界
**设计目标**：玩和写库分开。对局只读已发布事件；模型只写库。

| 场景 | MVP | V2（可选） |
|------|-----|------------|
| 对局第二段 | 只抽事件库；空则无事发生 | 仍默认抽库；可开 `LlmEventWriter` 临时补一条，建议事后再走 `LlmEventAuthor` 落库 |
| 录入 | 手填，或 `LlmEventAuthor` 生成草稿 → 校验 → 发布 | 同左，可加批量/向量去重 |

*   **模型不得**：对局中改存档；不经草稿发布就进合格池；发明未注册物品却当正式结果。

## 第二部分：游戏设计
### 2.1 游戏概述
**游戏名称**：《太一仙途》
**类型**：开放式文字修仙（单机），脑洞输入，随机剧情
**操控**：单主角，只打字。
**与传统游戏的差异**：无技能栏、无任务、无章节。剧情顺序不预写死；玩家写下一步，系统用**已发布事件库**接龙。大模型只在录入时帮写新事件。
**核心理念**：命令改状态，库内事件再改状态；库越厚接龙越丰，用模型扩库而不是对局现编。
### 2.2 核心循环
```
玩家文字命令
  → 第一段：命令型 GameEvent 改状态（到哪、做了什么、时间/饱食/金钱…）
  → 第二段：按新状态从事件库随机（抽空则无事）
  → 事件再改状态，并输出叙述
  → 玩家再脑洞下一句
```

状态机仍是空闲 / 行动中 / 闭关 / 等玩家回话 / 死亡。第二段抽空则只保留第一段（吃完饭，酒楼无事）。

#### 2.2.1 玩法示例（非主线，可整段抽不中）
背景：太乙历一百年，玩家 A 生于某某城，今年六岁。

1. 输入「去酒楼吃饭」→ 地点=酒楼，时间过一刻，扣饭钱，饱食上升。
2. 系统按「酒楼 + 六岁 + 白日」从事件库抽；有金龙鱼则叙述并设焦点，没有则酒楼无事（不对局问模型）。金龙鱼须事先手填或 `LlmEventAuthor` 入库。
3. 输入「去围观」→ 第一段：位置凑近摊位；第二段可能续：摊主叫卖、围观人群。
4. 输入「把鱼买下来」→ 有钱则扣钱得鱼；没钱则买不成，剧情改道。有钱后续仍随机：鱼是龙所化 → 报酬进背包/因果。
5. 另一次随机可能是：碰到修仙门派弟子。输入「请求加入门派」→ 按年龄/资质谓词决定收、拒、或让你再来；收了则写 `CauseLink(拜师)`、出身/身份变化。

以上每一步都可以抽成别的事，重开不会重演同一条。
### 2.3 功能系统设计
#### 2.3.1 万年历与天象系统
*   **UI 设计**：界面右上角设计一枚动态旋转的“罗盘”或显示古朴的“干支历牌”。
    *   显示示例：“太乙历 九四七六年 甲辰年 三月十五 午时”
*   **玩法机制**：
    *   **闭关**：只加速当前主角的结算（见 1.6），用于跳过枯燥修炼期；不把世界内 NPC 一起快进。
    *   **灵气潮汐**：每月初一、十五全局灵气浓度提升，修炼效率倍增，同时也是妖兽狂暴期。闭关跨越潮汐日则按“错过/赶上”规则结算一次加成，不重复刷。
    *   **天劫**：日历可推算“若抽中天劫事件、且境界已到”的可能窗口，不是主线预约。窗口内仍走随机，可能一直抽不中直到寿元耗尽。
#### 2.3.2 虚拟地图与探索
*   **世界生成**：
    *   **宏观**：一份手编世界地图，可在编辑器中增改城市与道路（V2）。
    *   **微观**：城市内按模板铺散修集市、宗门山门、遗迹、秘境等节点；进入建筑加载子图。
*   **探索玩法**：
    *   **神识扫描**：玩家使用神识技能扫描当前节点，可能发现隐藏点位（如“伪装成枯井的洞府入口”）。
    *   **动态变化**：如果玩家在某个地点引发大火，地图节点属性变为“废墟”，后续探索将触发生存类事件而非探险类事件。
#### 2.3.3 虚拟人物
*   **人物生成**：
    *   NPC 具有初始属性：资质、性格、运势、出身。
    *   **履历系统**：可见 NPC 用短模板生平；细履历按 1.5.1 预算展开。例如：“王麻子，20岁时因资质平庸被逐出师门，30岁时在坊市摆摊算卦为生”。
*   **生活模拟**：
    *   **日常事件**：NPC 日程只提高某类事件权重，仍从合格池随机；与玩家同一模型。
    *   **社交网络**：关系变化通过 `CauseLink` 驱动。杀死某 NPC 后，其亲友获得仇恨标签，可能发布追杀令。
#### 2.3.4 命令与随机剧情（玩家侧）
*   只打字。第一段改“我在哪、刚做了什么”；第二段只抽已发布事件。库空不加戏。
*   缺故事去**录入页**用大模型生成并发布，下次对局才能抽到。
*   无任务引导。金龙鱼、拜师都不是必经。
*   流程图只包一条事件内部（买 / 不买），结束即散。
时间与留存见 1.6。
### 2.4 数值系统
**设计目标**：为“突破”“顿悟”“走火入魔”等叙事概念提供可计算的数值骨架，避免沦为纯文字描述。

*   **属性体系**：
    *   **先天**：灵根（五行偏向）、资质（修炼速度倍率）、运势（奇遇权重）、出身。
    *   **后天**：修为、境界、寿元、心魔、悟性、饱食度、心境。
*   **境界与突破**：境界链 `凡人 → 练气(九层) → 筑基 → 金丹 → 元婴 → 化神 → 渡劫 → 大乘 → 仙人`。突破成功率公式（示意）：
    `P(突破) = clamp(资质×灵气浓度×丹药加成 − 心魔 − 境界惩罚, 0.05, 0.95)`。
    失败后果：修为回退一定比例，心魔上升；极端失败触发走火入魔（状态“癫狂”，随机行为 N 游戏日）。
*   **寿元与时间流速**：寿元以游戏时间为单位消耗。闭关加速时间流速时寿元同步加速消耗（闭关 100 年 = 寿元 −100）。寿元耗尽触发 `寿命耗尽` 事件，进入死亡流程（见 2.5）。
*   **灵气浓度**：由万年历（初一/十五加成）与地点属性共同决定，作为修炼效率与突破成功率的全局乘子。
*   **战斗与物品**：检定与背包见 1.10；丹药加成、食物饱食都从物品表读效果，不在突破公式里写死物品名。
*   **数值锚点**：以“练气一层到九层”为新手期（约 10 游戏年），筑基到金丹为中期（约 50 游戏年），金丹以上为长线。具体数值在数值表 `BalanceTable` 中集中配置，便于调优。

### 2.5 死亡与重玩机制
**设计目标**：让“寿元耗尽”“天劫身死”成为有张力而非劝退的体验，保证长周期游戏可挽回。

*   **死亡触发**：寿元归零、天劫失败、走火入魔未救治。发布 `DeathEvent`。
*   **死亡处理流程**：
    1.  结算角色 `Biography`，生成“生平碑文”存档。
    2.  清理该 Agent 的日程、未完成的 `GameEvent`、社交关系中的“在世”标记（关系不删除，转为“亡故”状态，可被后人查询）。
    3.  触发亲友反应：关系网中亲密度高的 NPC 发布“报仇/守孝”事件。
*   **重玩路径（三选一，由玩家在死亡时选择）**：
    *   **转世**：保留部分资质与悟性，重置境界与寿元，以“凡人”身份重新开始；可继承部分未过期 `CauseLink`（仇人可能寻上门）。
    *   **夺舍**：金丹以上境界可选，以残魂状态夺取一名 NPC 躯体，继承其身份与社交关系，但境界下降一级、心魔大增。
    *   **继承**：选择一名已存在的弟子/后代角色作为新主角继续游戏，继承部分资源与未过期 `CauseLink`，不继承“未完成主线”。
*   **NPC 死亡**：NPC 死亡同样走 `DeathEvent` 流程，其日程从全局调度中移除，未触发的库内事件（如“传授秘籍”）若有时限则作废，否则可由继承人触发。

### 2.6 数据流示例
背景：太乙历一百年，A 生于某某城，六岁。
1. 命令「去酒楼吃饭」→ 命令事件：地点=酒楼，饱食+，金钱−。
2. 用新状态抽**已发布**酒楼事件；有则金龙鱼，无则无事。
3. 命令「去围观」→ 凑近摊位；再抽库内围观向事件。
4. 命令「把鱼买下来」→ 谓词查金钱；成功则物品+金龙鱼，金钱再−。后续随机：鱼化龙、给报酬。
5. 另轮抽中门派弟子；命令「请求加入」→ 写或拒写拜师 `CauseLink`。
全程无主线指针；同背景下一局可以完全是别的酒楼故事。

## 第三部分：技术方案
底座是事件驱动的。模式用来固定**事件从产生到落地**的路径，而不是为用模式而堆模式。一条事件的默认路径：

```
生产者 publish
  → EventBus
  → EventArbiter（能否执行 / 入队 / 丢弃）
  → 责任链（可选：校验 → 扣资源 → 改状态 → 写因果 → 持久化）
  → 对应 EventHandler 策略（差异化业务）
  → 状态机（Agent / Location 变迁）
  → 可能再 publish 下游事件
```

读档时走另一条：事件日志 `type` → `EventRegistry` 工厂反序列化 → 重放进总线。

### 3.1 观察者模式：事件总线
**落点**：`EventBus` 是唯一发布入口。`ChatParser`、事件库检索、`GameClock`、日程都只 `publish`。MVP 对局路径上**没有** `LlmEventWriter`。

*   **订阅**：`GameEventHandler` 执行结果池改状态；聊天 UI 订叙述。
*   **同步投递**：命令事件与随后的库内奇遇分两次 publish，奇遇在命令结算之后。
*   **聊天解析失败**：不进总线，回文说明；不调用大模型编一条对局事件。扩库请去录入编辑器。

### 3.2 策略模式：事件处理器
**落点**：系统事件（时间、地图、死亡）各用一个策略；**事件库中的一般事件共用一个 `GameEventHandler`**，按该条事件的结果池执行（扣物品、加修为、突破检定、拉起流程图），不再为吃饭/打坐/突破各写一个 Intent 类型。

| 事件类型 | 策略职责（示例） |
|----------|------------------|
| `TimePassEvent` | 刷新天气、灵气；检查日程是否该 publish 库内事件 |
| `GameEvent` | 执行元数据与结果池：`eat` / `meditate` / `breakthrough` / 奇遇共用 |
| `MapUpdateEvent` | 改地点状态 |
| `DeathEvent` | 走 2.5 结算 |

结果池里的“突破检定”“战斗检定”是结果类型，不是独立总线事件。需要走火入魔时由结果 `chain` 再 publish 一条 `force` 的 `GameEvent`。

*   **差异化逻辑**进结果类型与谓词，不在总线里写 `switch 吃饭/突破`。新增生活行为 = 录入一条事件，不改投递核心。
*   **策略无状态**：可读写传入的 `World` / `Agent` 上下文，自身不缓存存档指针，便于测试和热替换。

### 3.3 状态模式：角色与世界变迁
**落点**：与 2.2 核心循环对齐。`Agent` 持有当前状态对象；非法指令在状态类内直接拒绝，不散落在 UI 和各个 Handler 里。

| 状态类 | 允许的转换 | 封装的逻辑 |
|--------|------------|------------|
| `IdleState` | → 行动中 | 接受命令型 `GameEvent` |
| `ActingState` | → 结算后空闲；强制级可打断 | 先结算命令，再挂接第二段随机事件 |
| `ClosedDoorState` | → 出关结算 | 局部加速；不改全局 `TimeDilation` |
| `EncounterPendingState` | → 空闲或继续行动 | 等下一句脑洞（围观/买鱼/拜师） |
| `DeadState` | → 转世/夺舍/继承 | 聊天只选重玩，不触发生活事件 |

世界侧对 `Location` 使用薄状态（如 `完好 / 废墟 / 秘境开启`），`MapUpdateEvent` 只触发状态对象的 `onEnter` / `onExit`（改灵气、换事件池标签），避免在地图节点上堆 if。

状态切换必须经状态对象的 `tryTransition`，成功后再 publish 如 `AgentStateChanged`，供 UI 和日程订阅。

### 3.4 工厂模式：事件注册表与反序列化
**落点**：`EventRegistry` 保存 `type → { 工厂方法, Handler, 优先级 }`。

*   **动态创建**：生产者只提交 payload + `type`（系统事件）或 `eventId`（库内 `GameEvent`），由工厂构造对象。`eat` / `meditate` / `breakthrough` 都是 `GameEvent` 的不同 id，不是不同 class。
*   **多态反序列化**：增量事件日志只存 JSON（`type` + 字段）。读档重放时 `EventRegistry.create(record)` 还原对象；未知 `type` 跳过并记警告，不让整档失败。
*   **版本**：注册项带 `schemaVersion`。旧存档字段缺失时由工厂填默认值，不在业务 Handler 里做兼容分支。

### 3.5 插件模式：处理器与生成器的加载
**落点**：`PluginLoader` 扫描并注册 Handler、事件工厂、以及生成器（规则生成器、V2 的 `VectorEventGenerator`）。

*   **MVP**：编译期静态注册（代码里 `registry.register(...)`），不做运行时热加载，降低存档与调试成本。
*   **V1+**：约定插件清单（名称、事件 `type`、依赖），启动或调试时加载。生成器与 Handler 同一套注册表，便于关掉向量插件后回退到纯规则粗筛。
*   **约束**：插件只能注册，不能替换 `EventBus` / `EventArbiter` / `GameClock`。插件 Handler 仍走仲裁和状态机，避免旁路核心规则。
*   **失败隔离**：单个插件加载失败不影响已注册核心事件（时间、死亡、存档）。

### 3.6 责任链模式：分步处理
**落点**：仲裁通过之后、主策略执行前后，事件沿一条短链传递。每个节点只处理自己关心的切面，可 `continue` / `stop`。

推荐链（固定顺序，避免插件随意插队到校验之前）：

1. **校验**：谓词、物品、状态是否允许（与状态模式配合）。
2. **资源**：扣饱食、丹药、时间锚。
3. **领域策略**：3.2 中的主 `EventHandler`。
4. **因果与日志**：写 `CauseLink`、追加事件日志。
5. **持久化钩子**：脏标记，不在此处做全量快照。

复杂事件（突破失败 → 心魔 → 可能走火入魔）用链内 `stop` 后由策略再 `publish` 强制级事件，而不是一条链上无限分叉。

**不要用责任链代替仲裁**：谁抢占、谁丢弃只在 `EventArbiter`；链只处理“已经获准执行”的事件。奇遇挂接是仲裁结果，不是链上某一个 Handler 的私自决定。

### 3.7 模式协作约束
*   新功能优先：能录入成 `GameEvent` 就不要新总线 `type`；系统级（时间、死亡、地图）才加工厂 + Handler。需要生命周期再加状态类；切面（日志、扣物品）才进责任链。
*   禁止 Handler 直接 `new` 未注册事件类型，必须走 `EventRegistry`，否则读档无法反序列化。
*   状态类不直接改背包或地图；通过 publish 让对应策略执行，保证日志完整。
*   单测最小集：总线投递顺序、仲裁丢弃、状态拒绝非法指令、工厂按 `type` 还原、链中校验失败不写因果。
