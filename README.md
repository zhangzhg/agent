# EventHorizon / 《太一仙途》

开放式虚拟修仙文字游戏。玩家用脑洞打字当输入；**对局输出只抽已入库事件**。没有主线，剧情全随机。大模型默认不参与对局接龙，只用于**把新事件写进事件库**。

本文是仓库里唯一的设计文档。字段、函数签名以源码为准；本文只记目标、不变量、玩法规格，以及已实现 / 未实现的边界。

**核心玩法**：

`玩家发送文字命令 → 先改人物状态（地点/时间/基础行动） → 再按新状态触发事件 → 事件再改人物状态`

核心诉求：

1. 虚拟地图 / 世界地图 / 城市地点的生成与编辑。
2. 事件录入系统：支持人物、地点（可为类型如“酒馆/酒楼”）、时间、持续时间、结果（秘籍、宝物、丹药正/负面、事件等）。场景可用前端流程图定制（仅单条事件内部）。可用大模型按同一结构**生成草稿并写入事件库**（须校验后发布）；对局中不现场生成。
3. 虚拟人物录入，按人物特征随机匹配事件，人物有出生时间（例：太乙历一百年、某城、六岁孩童）。
4. 事件触发概率生成器：命令落地后，按**当前状态**从合格池加权随机（向量可辅助）；无“下一章”。
5. 吃饭、打坐、突破、围观、买鱼、拜师等与奇遇同一套事件模型，一律由聊天命令或事件连锁触发。
6. 全局万年历生成器（有界面），可设置游戏时间与现实时间的比例。

**输入 / 输出**：输入只有玩家脑洞文本。对局输出 = 事件库抽中的叙述 + 结构化状态差分。大模型只出现在录入侧：描述想法 → 填表草稿 → 校验 → 发布入库，之后对局才能抽到。对局侧有一处有意识的例外，见 [§1.12](#112-对局输出与模型边界)。

| `CauseLink` | 因果标签：谁对谁做了什么 |
| `Biography` | NPC 生平履历 |
| `BalanceTable` | 集中配置的数值平衡表 |
| `AgentEventHistory` | 记录 Agent 最近触发事件与标签的滑动窗口 |
| `NoveltyWeight` | 重排阶段的新鲜度乘子 |
| `EventVariant` | 同一 `GameEvent` 下的多条叙述文案 |
| `AppliedDiff` / `WorldDiff` | 唯一改 Agent / World 的差分；实时对局与读档重放共用 `apply_*` |
| `Pending*` | Agent 上的挂起态，必须进快照：奇遇 / 流程图 / 闭关追问 / 创作追问 / 延迟结果 |

# 第一部分：底座设计

## 1.1 概述

基于 EventHorizon 的通用事件驱动底座，针对文字修仙（高自由度、长周期、复杂因果、叙事多样性）在时空、叙事、检索、模拟四个维度做扩展。

**产品边界**：单机、同一世界库可有多名玩家人物。开局须**建立人物**；进入游戏须输入**人物 id + 验证码**。物品与属性永久保存；任务/奇遇等事件快照只保留 **3 个墙钟日**，逾期再进入则清挂起任务、保留修为与行囊。开放式文字沙盒：操作入口是**聊天框**，不是技能栏或任务面板。类型为文字修仙；物资消耗只做到生存层，不做工坊经营。文中“全局”指当前存档世界。

**无主线**：不实现任务日志、章节、必经 BOSS、既定结局。引擎不调度“故事进度”。玩家想成仙、复仇或活下去，只能通过聊天触发事件、改状态去碰，事件可被错过、可永不发生。

**玩法核心**：两段状态变化。第一段由玩家命令落地；第二段只从事件库随机抽（抽空则酒楼无事）。聊天原文不直接改数值。

**技术前提**：Python 3.11+；`dataclasses` + `typing.Protocol`；持久化用标准库 `sqlite3`。MVP **回合驱动**——游戏时间只由事件的 `duration_shichen` 推进，不开墙钟线程。

**分期交付**（对照当前代码）：

| 分期 | 目标 | 现状 |
|------|------|------|
| MVP | 手填地图、万年历、事件库接龙、聊天命令、建角/验证码进游戏、存档、新鲜感基础；对局关闭大模型；录入可用 `LlmAuthorPort` | 已落地 |
| V1 | 流程图 JSON + 聊天选分支；日程与关系网；`EventArbiter`；`CauseLink`；标签配额与长尾保护 | 已落地 |
| V2 | 向量匹配、可选对局临时生成、地图编辑器、转世/夺舍 | 机制已落地；内容与部分 UI 未齐 |

### 分层与目录

```
controller/          请求入口：解析输入、调度 model、选 view
model/
  domain/            纯业务模型，零外部依赖，无 IO
  services/          用例编排；ports.py 定义 Protocol
  repositories/      SQLite、Embedding、录入侧 LLM 适配器（实现 Protocol，反向注入）
view/                只消费 TurnResult / AppliedDiff，不依赖 PipelineContext
content/             MVP 世界地图、事件库、物品定义
```

依赖方向：`controller → model.services → model.domain`。对局唯一入口是 `PlayTurnService`：仲裁 → 谓词校验 → 状态机 → 责任链产出 diff → 一次性 apply → 记日志 → 再决定是否抽第二段。状态类不持有 `EventBus`。

**禁止**：在 `controller` 里直调 `pipeline.run` / `coarse_filter`；在状态类里改背包；结果池执行器直接写 `Agent` 字段；服务对象持有跨回合状态；对局路径注入 `LlmAuthorPort`。架构守卫见 `tests/test_layering.py`。

## 1.2 时空服务

### 1.2.1 万年历

时间结构：`纪元 → 年(干支) → 月 → 日 → 时辰`。一年 `SHICHEN_PER_YEAR = 12 × 30 × 12 = 4320` 时辰。`GameClock` 是唯一权威时间源，按 `TimeDilation` 推进（MVP 恒为 1），发布 `TimePassEvent`。特殊日期（每月初一、十五的灵气潮汐）走日历判断，不是主线预约。

`advance_for` 推进时钟的同时：按跨度扣寿元（`shichen / 4320` 年）、按历法年差加年龄。日常命令与闭关共用这一条账。

### 1.2.2 虚拟地图

图结构：`Location` 节点（类型、灵气、危险等级）+ `Route` 边（连通与消耗）。世界层手编；城市内节点按模板生成；建筑内部按需加载嵌套子图。节点剧变走 `WorldDiff`（属性改写 + 新增地点/路线）。`WorldDiff.invert()` 只能对调属性改写，新增拓扑无法无损反演。

## 1.3 叙事引擎

### 1.3.1 流程图

`ScenarioGraph` 只包**单条事件内部**分支，禁止引用主线步骤 / 章节 id。边条件只允许谓词白名单（`AND` / `OR`），执行器不做字符串 `eval`。进度存在 `Agent.pending_scenario`，必须进快照，推进必须走 `AppliedDiff.pending_scenario_set`。

### 1.3.2 事件库

吃饭、打坐、突破、奇遇、归宿**同一套 `GameEvent` 模型**。元数据：适用地点/类型、时间、前置谓词、权重、冷却、次数、互斥标签、优先级、标签、聊天别名。`TriggerSource` 只是本次投递字段，不是事件类型。结果池：物品、状态、检定、`CauseLink`、连锁、绑定流程图。

草稿不进合格池；发布后才参与抽取。

### 1.3.3 录入编辑器

三层：事件列表 → 详情表单 → 内嵌流程图。谓词构建器 / 结果池 / 文案变体 / 测试沙盒与运行时共用同一套校验（`event_validation.py`）。Web 管理后台在 `controller/admin_controller.py` + `view/templates/`。

### 1.3.4 大模型辅助入库

编辑器内「用描述生成事件」→ `GameEvent` JSON 草稿 → 与手工保存同一套校验 → 人工发布才进合格池。`ChatParser` / 第二段抽取 **不调用** `LlmAuthorPort`。库空只输出「无事发生」。

录入侧实际是一组 Adapter（地点 / 物品 / 事件风味 / 结果文本），共用 `LlmClient`。配置缺失不能让服务起不来。AI 产出的结果池先过 `result_pool_safety.sanitize_result_pool`。

## 1.4 事件匹配：规则粗筛 + 向量重排

单纯向量检索会在闭关时抽到走火入魔；单纯规则会无视处境。采用漏斗：

1. **硬性规则筛选**（地点、时间、境界、谓词、冷却、次数、互斥）→ 合格池。逻辑不正确的事件这一步就必须出局。
2. **向量语义匹配**（可选）：把人物处境写成自然语言查询文本，与候选事件描述比余弦相似度，作叙事贴切度乘子。向量失败 fail-open 成中性权重，不崩回合（`embed_safely`）。
3. **加权随机 + 新鲜感**：短期记忆衰减、标签配额、长尾保护、文案变体。全部乘子只作用于重排，不改仲裁与状态机。

查询文本不要直接丢结构化字段，要写成修仙风味自然语言（例如“身受重伤的修士深夜迷失在万毒谷……”）。事件 embedding 在录入时预计算。真实向量与本地哈希词袋维度不同，混比直接判 0——宁可判不匹配，不要假匹配。

MVP 可关向量模块，只走元数据过滤 + 权重随机。

**禁止项**：全局 `questId`、章节解锁、强制下一事件队列（`force` / `chain` 除外）。

## 1.5 智能体生命周期

**NPC 履历**：仅对同城、带未过期 `CauseLink`、或玩家查询过的 NPC 展开细履历（步数上限约 8）；其余用模板一句。细模拟同样从事件库抽。

**日程**：`Schedule` 把某时辰的权重偏向某一标签，**不保证**必触发。空闲且时辰命中时以 `TriggerSource=schedule` 走同一条 `execute_occurrence`。全量 NPC 都跑日程会随世界变慢，预算规则需要硬上限（仍开放）。

## 1.6 时间模型

全局主时钟 + 个体时间锚，而非每个 Agent 独立时钟。

- 闭关 = 局部加速结算：推进该主角的 `pendingDuration`，寿元同步消耗；不改全局 `TimeDilation`，不把全世界一起快进。
- 离线时主角锚点不随墙钟空转。
- 与全局事件交互时以时间锚偏差决定“错过”，而非强行对齐。

## 1.7 事件仲裁

| 等级 | 来源 | 行为 |
|------|------|------|
| Force | 天劫、走火入魔、死亡 | 立即中断 |
| Player | 聊天命中 | 抢占日程 |
| Schedule | 日程抽中 | 可被聊天抢占 |
| Encounter | 粗筛后随机 | 仅空闲/探索时挂接 |

同一 Agent 同一时刻只能处理一个主行为。`ENQUEUE ≠ EXECUTE`：acting 时 encounter 入队且不执行结果池。

## 1.8 持久化

- 快照 + 自上次快照以来的增量日志。读档：载入快照 → `replay_since`（**严格大于**快照时刻）→ 逐条 `apply_agent_diff` / `apply_world_diff`。不进总线、不 matching、不跑 pipeline。
- `GameTime` 落盘为整数 ordinal（自 year=0 起的时辰数）。旧档 `{"epoch","year","month","day","shichen"}` 仍能读，避免换格式丢档。
- Occurrence JSON **必须含 `applied_diff`**；改了地点还须含 `world_diff`。事件历史走 `history_records`，否则重放会丢冷却/新鲜度。
- 挂起态必须进快照。缺 `applied_diff` 的旧日志视为损坏，跳过并告警。
- 快照保留最近 N 份；世界无变化不写世界快照。每次 Agent `save()` 删掉 ordinal ≤ 快照时刻的日志（已烤进全量快照，留下只会把库撑到写失败）。`replay_since` 的严格大于边界修过真实的重复应用 bug，不要改松。
- **人物身份**：`player_characters` 存人物 id、验证码哈希、事件快照墙钟。验证码只在建角时明文返回一次。进入游戏时按当前人物事件存档恢复；若墙钟超过 3 天则清 `event_history` 与全部 `pending_*`（死亡除外），**金钱、修为、行囊、境界、地点永久保留**。NPC 不进这张表。

## 1.9 因果模型

`CauseLink`：`Actor`、`Action`、`Target`、`Tag`、`ExpiresAt`。结果池、死亡、流程图节点可写入。读取方：谓词 `has_cause`、关系网、转世时可继承部分 Tag。只存标签与过期，不存自由文本推理。

## 1.10 物品与战斗（薄层）

物品含类型、堆叠、正负面效果；没有生产链。战斗是文字检定：`P(胜) = clamp(境界差 + 道具 + 运势 − 心魔, 0.05, 0.95)`。

## 1.11 文字命令

`ChatParser`：一句话 → `{ 地点?, 行动, 对象?, args }`。**别名表先于移动正则**——“去吃点东西”命中 `eat`，不会被当成目的地“吃点东西”。别名匹配最长优先，避免短别名永久遮死长别名。

第一段发布命令型事件；谓词不过则不抽第二段。流程图内选择也用下一句聊天。

代词（“它”/“这个”）：及物动词缺宾语时用 `agent.scene_focus` 回填。

只读查询（打听 NPC、扫描、世界问答）由 controller 在两段循环之外处理，不改状态、不消耗回合、不进 `AgentEventHistory`。

## 1.12 对局输出与模型边界

| 场景 | 默认 | 可选 |
|------|------|------|
| 对局第二段 | 只抽事件库；空则无事 | 可开 `LlmEventWriter` 补文案；建议事后走录入落库 |
| 录入 | 手填，或 `LlmAuthorPort` 草稿 → 校验 → 发布 | 可加批量 / 向量去重 |

模型不得：对局中改存档；不经草稿发布就进合格池；发明未注册物品却当正式结果。

**例外（有意识的产品决策）**：`LiveContentAuthor` 只服务“规则解析 + 向量意图都处理不了”这一个场景。创作的新命令/地点立即落库生效。`LlmAuthorPort` 的隔离边界没有变，不要把这条旁路当成守卫名存实亡。

创作前多两道核实：地点创作可 `list_locations` 查重；信息不够则 `PendingClarification` 追问（最多 3 次，问满回落 §1.13）。挂起态进快照、参与 `AppliedDiff` 合并。

Agent 上现有挂起态：`pending_encounter_id`、`pending_scenario`、`pending_retreat_prompt`、`pending_clarification`、`pending_live_result`。漏序列化会读档静默丢状态。

对 `glm-4-flash` 的防护（漏填 `result_pool` 给默认值、数值 clamp、示例占位符拒绝）每条背后都有实测坑，换更强模型前不要拆。

## 1.13 输入解析兜底链

原则：**不要拒绝，要“理解并转化”**，即使转化结果是无意义的消耗。玩家聊天框里能打出任何话，`handle_player_text` 按下面这条链依次尝试：

1. **`ChatParser.parse`**——别名精确/子串匹配（“吃饭”→`eat`）。
2. **向量意图兜底**——与当前地点已发布命令的 `narrative_embedding` 比语义相似度。
3. **`LiveContentAuthor` 实时创作**——前两层都判断不了时现场创作；必要时先追问。
4. **终极兜底：`idle_wander`**——前三层全部落空（模型 `reject`、追问满 3 次、地点创作失败）时，**绝不再显示干瘪的“听不懂”**，执行预置闲逛命令：旁白 + 消耗一点时间。它本身也是带别名的库内事件，含糊输入往往第 2 层就已经命中。

前 3 轮走到终极兜底时仍显示软性引导（举当前地点命令别名当例子），第 4 轮起才执行 `idle_wander`。

纯 ASCII 会被判为乱码直接拒绝（中文游戏边界；`meditate` 这种英文词目前走不通）。

## 1.14 世界信息问答

“我在哪里”“附近有哪些城市”走独立只读路径，不进 §1.13。关键词粗筛 → `WorldQueryAssistant` function calling（`get_player_status` / `list_reachable_locations` 等）→ 先拿真实数据再作答。模型判断不是在问信息时返回 `None`，**原样回落命令解析链**，不能截胡正常指令。

## 1.15 延迟结果

实时创作事件可带 `deferred_result_pool`：当下不兑现、故事线收尾后才落地（如“扬言日后报复”）。记在 `PendingLiveResult`。每轮判断是否翻篇；满 3 轮（含没配模型）强制落地。挂起期间不抽第二段随机奇遇。手工录入的内置命令不走这套。

## 1.16 分支结果

实时创作可带 `reply_options`（至少 2 个合法分支），与库内 `needs_reply` 奇遇复用同一套挂起。宿主事件自己的 `result_pool` 强制清空。

**时间语义（产品决策）**：分支不消耗游戏时间——玩家在已经发生的场景里做选择，不是又过了一个时辰。只有主命令和第二段奇遇调用 `_charge_time`。

**历史语义（与时间解耦）**：挂起时仍记入 `event_history`（冷却 / 次数 / 新鲜度生效）；选分支时不再记第二次。选分支的 `results` 照常结算。买不起时拒绝并保持挂起（“你囊中羞涩”），金钱下限为 0。

流程图节点同样不计时、不重复记历史、不可负担则拒绝。

# 第二部分：底层不变量

这些约束支撑“实时对局与读档重放共用同一份 apply”，改行为前先读对应测试。

1. **diff 是唯一状态写入口**。结果池只计算 diff。例外：`DeathService.reincarnate/possess/inherit` 是文档标明的单独用例，直接改写同一 `agent_id`（重玩不是重放存档）。
2. **`replay_since` 严格大于**快照时刻，避免快照边界的 duration=0 事件被应用两次。
3. **状态切换必须经状态对象 `try_transition`**，成功后再 `publish(AgentStateChanged)`。
4. **谓词白名单，禁止 `eval`**。
5. **服务对象无跨回合状态**；挂起全在 Agent 上，必须快照。
6. **`LlmAuthorPort` 不得进入对局路径**。`LiveContentAuthor` / `LlmEventWriter` 是不同端口。
7. **`embed_safely` fail-open**：向量出问题退化成中性权重。
8. **`ENQUEUE ≠ EXECUTE`**。
9. **单线程、回合驱动**；总线队列不上锁。V1 若接墙钟，只改 `GameClock` 驱动方式，`advance_for` 以下不动。
10. **插件不能替换** `EventBus` / `EventArbiter` / `GameClock`。

事件默认路径：

```
生产者 publish → EventBus → EventArbiter（执行 / 入队 / 丢弃）
  → 责任链（校验 → 资源 → Handler → 因果与日志 → 脏标记）
  → 状态机 → 可能再 publish 下游
```

责任链不代替仲裁。新功能优先录入成 `GameEvent`，系统级（时间、死亡、地图）才加工厂 + Handler。

模式落点：观察者 `event_bus.py`；责任链 `pipeline.py`；策略 `handlers/*`；状态 `states.py`；工厂 `registry.py`；端口/适配器 `ports.py` + `repositories/*`。

# 第三部分：游戏设计

**游戏名称**：《太一仙途》。类型：开放式文字修仙（单机），脑洞输入，随机剧情。无技能栏、无任务、无章节。

**体验目标**：核心情感曲线是“意外感曲线”不是“变强曲线”。三条原则：永远不让玩家觉得抽到了标准答案；失败也要有内容（说出为什么）；不用进度条制造焦虑（寿元用模糊态）。

## 3.1 核心循环

```
玩家文字命令
  → 第一段：命令型 GameEvent 改状态
  → 第二段：按新状态从事件库随机（抽空则无事）
  → 事件再改状态，并输出叙述
  → 玩家再脑洞下一句
```

状态机：空闲 / 行动中 / 闭关 / 等玩家回话 / 死亡。死亡后聊天只选重玩（转世 / 夺舍 / 继承），不触发生活事件。

玩法示例（非主线，可整段抽不中）：太乙历一百年，六岁孩童「去酒楼吃饭」→ 抽金龙鱼或无事 →「去围观」→「把鱼买下来」过金钱谓词。每一步都可以抽成别的事。

## 3.2 界面与交互

聊天框是唯一操作入口，其余面板只读。

| 面板 | 规格 | 实现 |
|------|------|------|
| 叙述滚动区 | 叙述 vs 系统提示两种气泡 | Web 聊天入口已有；样式未完全按稿 |
| 历法牌 | `太乙历 … 甲辰年 三月十五 午时`，潮汐日标记 | **已实现** `calendar_view.render_calendar_plaque` |
| 罗盘动画 / 天劫暗红光晕 / 点击展开 CosmicEvent | 氛围提示，不是倒计时 | **未实现**（只有 `shichen_index` / `is_tidal_day` 数据） |
| 角色面板 | 境界+修为条；寿元模糊态；心魔不展示；饱食五格 | **已实现** `character_panel_view` |
| 位置面板 | 地点名+类型+灵气；不放跳转列表 | **已实现** `location_panel_view` |
| 背包 | 堆叠列表，无“使用”按钮 | **已实现**数据组装；图标/tooltip 交互未齐 |

## 3.3 命令语言

|----------|------|----------|------|
| `move` | 系统命令 | 「去{地点}」「前往」 | 已实现 |

## 3.4 标签与内容密度

标签：`生活` / `修炼` / `奇遇` / `社交` / `天劫` / `环境`。奇遇长期占比目标 15%–25%。

密度原则：每个「地点类型 × 标签」MVP 至少 6 条不同 `event_id`，总量目标约 **80–90** 条。当前内容包约 **54** 条（苍梧/落雁/藏剑/黑风/归墟 + 通用命令），低于密度线——新鲜感机制只能轮换已有事件，**填不满的池子机制救不了**。这是内容债，不是引擎债。

## 3.5 万年历、潮汐、闭关

- 灵气潮汐：每月初一、十五，灵气 ×1.5，修炼收益同比例，妖兽权重 ×2。闭关跨潮汐日只结算一次加成。
- 天劫窗口：境界到渡劫后权重从 0 抬到非零，仍是概率，可能一直不中直到寿元耗尽。不做定时器预约。
- 闭关：「十年」「到金丹为止」或「随便」。`随便` 给出建议年数并要求玩家打出确定年数，不直接开跑。抽中天劫/走火入魔时以 `TriggerSource.FORCE` 执行 `qi_deviation`，不是只改叙述。寿元耗尽进入死亡。

## 3.6 地图与人物

MVP 世界：苍梧城、落雁镇、藏剑山门、黑风谷、归墟秘境（隐藏）。城市内部模板（集市/主街/城门 + 随机酒楼等）部分手编，未做成完整程序化铺点。地点废墟态的叙述钩子未普遍落地。

NPC：灵根/资质/运势/出身；模板履历 vs 细履历。社交变化走 `CauseLink`。

## 3.7 数值

境界链：`凡人 → 练气(九层) → 筑基 → 金丹 → 元婴 → 化神 → 渡劫 → 大乘 → 仙人`。集中在 `BalanceTable`。

```
P(突破) = clamp(资质×灵气浓度×丹药加成 − 心魔 − 境界惩罚, 0.05, 0.95)
```

寿元以游戏时间为单位消耗。闭关 100 年 = 寿元 −100。寿元耗尽发布 `DeathEvent`，进入死亡流程。练气一层到九层约 10 游戏年为新手期。

经济：吃饭 2–5；奇遇 5–50；拜师礼 50–200。新手期收支紧平衡。

心魔/悟性/运势不在面板展示，只通过叙述与检定侧面体现。

## 3.8 死亡与重玩

触发：寿元归零、天劫失败、走火入魔未救治。处理：碑文、清全部挂起态、亲友反应（内容未齐）。

三选一（打字，不是按钮；未达条件的选项说明原因而非隐藏）：

| 路径 | 规则 | 实现 |
|------|------|------|
| 转世 | 同一 `agent_id` 重置境界/寿元/年龄；保留 50% 资质偏差、50% 悟性与气运；可继承仇恨/拜师因果 | **已实现** |
| 夺舍 | 金丹以上；附近须有 NPC；境界降一级、心魔大增 | 机制已实现；无 NPC 时不可选 |
| 继承 | 须有弟子/后辈 NPC；继承部分资源与因果 | 机制已实现；无合适 NPC 时不可选 |

# 第四部分：技术方案摘要

`EventBus` 是唯一发布入口。系统事件（时间、地图、死亡）各用一个策略；库内一般事件共用 `GameEventHandler`，按结果池执行。

| 状态类 | 允许的转换 |
|--------|------------|
| `IdleState` | → 行动中 |
| `ActingState` | → 结算后空闲；强制级可打断 |
| `ClosedDoorState` | → 出关结算 |
| `EncounterPendingState` | → 空闲或继续行动 |
| `DeadState` | → 转世/夺舍/继承 |

责任链固定顺序：校验 → 资源 → 领域策略 → 因果与日志 → 持久化脏标记。不要用责任链代替仲裁。

录入侧 AI、embedding 兜底、Web 管理后台已落地，分层约束没变。`WorldView.mutable_state()` 与“只读”表述有张力，写入应继续只经 `WorldDiff`。
